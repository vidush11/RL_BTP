## 1. "Use the given GVFs as prediction also"

**Interpretation.** The "given GVFs" are the RL_BTP Horde demons. They are used in two ways, each fully alongside the paper's own GVFs:

1. **They learn on this simulator, from the same behaviour stream as the paper GVFs.**
   - In a `gvf` run, every transition generated by μ updates the paper GVF bank (Algorithm 1) *and* the unedited RL_BTP `Horde.update` (GQ(λ), tile coding).
   - The Horde is fed through `agents/horde/adapter.py`.
   - μ's probability for the taken action is passed as `mu`, so the Horde's importance-sampling ratios are correct.
2. **They drive a second predictive controller (`agents/horde/controller.py`).** It is built the same way as the paper controller, but asks the RL_BTP questions:
   - `steps-to-obstacle(FORWARD)` and `steps-to-stop(STOP)` give a slack. A small slack means danger.
   - `bump-soon(FORWARD)` gives a collision probability.
   - In danger, the controller acts greedily on `avoid-front-obstacles [ctrl]`, over the non-FORWARD actions.
   - Its thresholds are tuned on validation seeds, exactly like the paper controller's.
3. **Their prediction quality is measured** against Monte-Carlo returns from the same states (`safety_exp/analyze.py::prediction_quality`). The paper GVFs are measured the same way.

So each `gvf` run gives two controllers, both learned off-policy from one data stream. They are reported separately, as "paper GVF controller" and "given GVFs (RL_BTP Horde)".

**Adapter (A6) differences from RL_BTP's own robot:**

| sensor | RL_BTP | here |
|---|---|---|
| IR_F / IR_L / IR_R | Rays to the arena walls only | The LiDAR beams nearest 0 and ±1 rad, with the same `exp(-d/0.6)` squashing. With 72 beams (5° apart), the side beams are at ±55°, the closest to ±57.3°. These rays also see obstacles. |
| sensor noise | N(0, 0.005) | none |
| LIGHT_L / LIGHT_R | RL_BTP formula | Same formula, light at (1.6, 1.6), with occlusion by obstacles. The light is a **sensor only**: it is not in the policy observation and not in the reward. It exists so the light demons have a non-trivial signal. |
| BUMP | — | 1 on the collision step |
| COMPASS | — | cos θ |
| VEL / ANG_VEL | — | the robot twist |

**Episode boundaries.** RL_BTP has no episodes; its robot bounces off walls.
- At each reset, the run loop zeroes the Horde traces (`horde.e[:] = 0`). This is done in the calling code, not by editing RL_BTP.
- The collision step is passed with BUMP = 1. That gives `steps-to-obstacle` its γ = 0 through the demon's own γ function.
- The other demons bootstrap through the collision state, because the unedited `Horde.update` has no termination input. The Monte-Carlo "truth" in the prediction-quality table stops at true termination, so this mismatch is visible in the table rather than hidden.

## 2. Hard requirements

- **H1 (episodes).**
  - A collision terminates the episode on the contact step. The contact test uses the swept disc, with `collision_lidar_threshold: null`.
  - On that step, the paper GVFs use γ′ = 0 and c_f is forced to 0. DQN uses a terminal mask on `terminated` only.
  - A time-limit truncation (800 steps) bootstraps in both methods.
- **H2 (bit-identical defaults).**
  - `tests/golden/golden_v1.pkl` was recorded *before* any simulator change (commit `be6231f`).
  - `tests/test_golden_regression.py` replays 10 configs. It compares observations, rewards, flags and the exact set of info keys.
  - Every new info key appears only when its feature is enabled.
- **H3 (opt-in, strict config).** Every new feature has a config switch that defaults to off. Unknown keys still raise `ConfigError`.
- **H4 (fairness).** Both methods use the same `configs/safety_task.yaml`, the same observation, the same 4 actions, the same 30,000-episode budget, and the same `evaluate`/`summarize` code on the same seeds. Two differences cannot be avoided, and are reported rather than hidden:
  - The GVF method is trained on μ's data, while DQN is trained on its own ε-greedy data. This makes the env-step counts differ, so curves are plotted against both episodes and env steps.
  - The GVF method's controller thresholds are an eval-only grid on validation seeds (§7).

## 4. Paper GVFs (Part B)

**Algorithm 1, implemented as written:**
- The replay stores (s, a, c, γ′, s′, a′), with a′ ~ π(·|s′, a) sampled at collection time.
- The target is y = (1−γ)c + γ′ q(s′, a′; θ), computed with the current θ.
- Semi-gradient squared loss on the taken action only.
- No importance sampling and no target network. `target_network` exists only as a labelled deviation and is off.

**Cumulant scaling.** Cumulants are scaled by (1 − γ), so predictions lie in [0, 1]. c_f = 0 whenever γ′ = 0, so the paper's (1 − γ_{t+1}) reading and the constant (1 − γ) reading give identical targets here.

**Cumulants.**
- Front safety c_f, from §3.
- Speed c_v = v_{t+1}/v_max. It uses γ′ = 0 at collision, like c_f; the speed after a crash is treated as 0.

**γ values.**
- The paper's set is {0.95, 0.975, 0.983}.
- The horizon-matched sweep is {0.90, 0.95, 0.967}, trained only in GVF seed 0 because of cost (`--sweep-gammas`). 0.95 appears in both sets and is trained once.

**Networks.** One network per γ, each with two |A|-sized output heads (safety and speed) on a shared trunk. The paper says there is one estimator per horizon and one output per cumulant; sharing the trunk between the two cumulants of the *same* γ is my reading of that.

**Hyper-parameters.**
- MLP 222-128-128-8, Adam.
- Replay 100k, batch 64, learning starts after 2,000 transitions.
- One gradient step per 4 env steps, the same ratio as DQN.
- The learning rate is tuned (§7).

**Policies (discrete analogues of the paper's continuous Gaussian/Wiener policies, `agents/gvf/policies.py`):**
- **Target π, "keep doing what I'm doing":** repeat a_prev with probability 1 − ε_π, otherwise pick uniformly among the other actions. ε_π is tuned.
- **Behaviour μ:** repeat with probability 0.70, switch with 0.25, and a uniform "interruption" with 0.05. Episodes start from STOP.
- μ ≠ π, so learning is off-policy, as in the paper.

**Controller (paper Alg. 3 then Alg. 2, `agents/gvf/controller.py`).** It looks up q = q_front(s, a_prev) for the selected γ.
- If q < β₁: argmax over the 4 actions of q_front, with ties going to STOP.
- If q > β₂: speed control. If v̂ = q_speed(s, a_prev)·v_max is below v_target − tol, choose FORWARD. If it is above v_target + tol, choose STOP. Otherwise keep a_prev.
- Otherwise (between the thresholds): keep a_prev, which gives hysteresis.
- tol = 0.01, because v_target + 0.02 would equal v_max and the "too fast" branch could then never fire. This was found by a failing unit test.
- `use_speed_gvf = False` uses the measured speed instead; it is a tuned option.

**Two-stage protocol.** At every evaluation, the predictors and the Horde are copied and frozen (`frozen_copy`, `frozen_horde`), then they drive on the evaluation seeds. Training continues on μ.

## 7. Tuning (equal budget, validation seeds only)

**Training runs.**
- GVF: 6 configs (lr ∈ {3e-4, 1e-3} × ε_π ∈ {0.05, 0.1, 0.2}).
- DQN: 6 configs (lr, γ, target period, ε-decay; see `safety_exp/tune.py`).
- Each run is 3,000 episodes on training seed 100, so both methods get the same training budget.

**Selection.** The metric for every method is mean task return on validation episodes (seeds 2,000,000+).
- **GVF controllers:** for each GVF run, an eval-only grid on 50 validation episodes:
  - paper controller: 36 points (γ × 6 (β₁, β₂) pairs × use_speed_gvf);
  - given-GVF controller: 24 points.

  The best paper-controller return picks the GVF predictor config.
- **DQN:** scored on 100 validation episodes.
- **Fairness caveat.** The controller grids are evaluation-only (no extra training), but they are still extra selection that DQN does not get. DQN's analogue would be selecting among checkpoints, which was not done. This favours the GVF side slightly and is stated in REPORT.md.
- The selected values are in `runs_safety/tuning/tuning.json` and are used unchanged by every 30k run.

## 8. Evaluation protocol (Part D)

| purpose | seeds |
|---|---|
| training | 0, 1, 2 (tuning: 100) |
| test | 1,000,000+ |
| hard test | 1,500,000+ |
| validation | 2,000,000+ |
| learning curve | 3,000,000+ |
| post-hoc analysis | 4,000,000+ |

The ranges are disjoint, and `assert_kind` checks every evaluation call.

**Learning curves.** Before training and every 500 episodes, on the same 100 curve seeds for every method and evaluation point.

**Final tests.**
- 1,000 test episodes.
- 1,000 hard episodes: 5 obstacles instead of 3, the same size range, a new layout every episode.

**Metrics, from one function (`summarize`) for every agent.** Survival is never reported without speed.
- collision-free rate;
- speed / v_target (it can exceed 1 because v_max = 0.22 > 0.2);
- task return;
- distance;
- near-miss fraction (steps with min LiDAR < 0.25 m);
- min-range percentiles;
- |ω|.

**Confidence intervals.**
- Curves: 95% bootstrap over seeds.
- Final tables: hierarchical bootstrap (seeds, then episodes). With 3 seeds, the across-seed spread is a rough estimate, and REPORT.md says so.

**Post-hoc analysis** (Fig. 4/5 analogues, γ/β ablation, prediction quality) uses the frozen final predictors of `gvf_s0` and the analysis seed range. Nothing is selected from it.

**Resume.** Checkpoints are written atomically every 2,000 episodes. A resumed run reseeds its env stream with `seed·1,000,003 + episode`, so it is valid but not bit-identical to an uninterrupted run.

## 9. Compute (measured before the full runs)

Cost per env step on one Apple-silicon core:

| component | cost |
|---|---|
| env + μ | 141 µs |
| paper GVF bank (3 nets, 1 update per 4 steps) | 161 µs |
| **RL_BTP Horde update (unedited)** | **739 µs** |
| DQN train | 56 µs |
| controller act, paper | 8 µs |
| controller act, Horde | 255 µs |

- μ episodes average 359 steps, so 30k episodes ≈ 10.8M env steps.
- Estimate per seed: about 4–4.5 h for GVF (the Horde update dominates and was deliberately left unoptimised, because it must stay unedited) and about 1–2 h for DQN. Measured wall-clock is in REPORT.md.
